## 1. What the plan commits to

**1.1 The question.** For a newly withdrawn source, the tool tells a team which mixtures need a successor, which records the successor can keep, which checkpoints have evidence of exposure, and what must be rebuilt to remove the source and anything derived from it, such as its translations [CHECKED: Part 1, "What we want"]. **1.2 Constraints the request sets (hard).**

## 2. Answer rules

**2.1 The four answers (Decisions 8 and 21).** An artifact's own record is the record that says what it holds: a shard's occurrence map, a mixture's snapshot, a checkpoint's run segment, a published model's link to its parent checkpoint. Per artifact (mixture, shard, checkpoint and, when that extension is on (1.4), published model) the tool answers one of:
- **contains**, with the chain of evidence; where the chain passes a generation edge, the answer adds that the parent list is process evidence (what the harness handed the job and what the output states it used) and not proof that the output depends on the source (Decision 25); a checkpoint's "contains" also states its basis (2.4);
- **may contain**, when the artifact's own record exists but a link is missing, weak or unverified: it names the first such link and lists the candidate sources among the inputs of the step that made the artifact;
- **does not contain**, only with a coverage proof, scoped to the source, run and steps the proof covers and, past a generation edge, to the reads its harness log shows (L8) and, with the generating-model extension on, to the model it shows (L11), and to the inputs registered under the source (L12); while that extension is off, an answer whose proof passed a generation edge states "generating-model exposure not assessed" (2.2(h));
- **not covered**, when the artifact's own record is missing, whether another record names the artifact (the answer says "record missing") or the store has never been told of it (the answer says "not registered"); a query about an unregistered artifact gets this answer and never a partial or approximate one. Anything downstream of such an artifact answers "may contain" naming the missing record, never "not covered" and never "does not contain".

**Listings (Decision 26).** A question over many artifacts (which mixtures need a successor, which checkpoints have evidence of exposure) gets a listing. A listing states the runs, mixtures, shards and checkpoints it covers, and lists as "not covered" every artifact that another record names (a mixture's snapshot names its shards, a checkpoint names its run segment and its parent checkpoint) but that has no record of its own. An artifact never registered and never named cannot appear in it (L10).

**2.2 The coverage proof (SONNET55-1, sonnet5.5).** `coverage.prove(artifact, request)` walks the artifact's ancestor closure on demand from the evidence store (3.4) and returns a proof object or the first failing link. The answer type has no way to build "does not contain" except from a proof. A proof holds only if all of these hold:
- (a) every occurrence in the artifact has a recorded chain back to ingested source revisions (for a checkpoint, every occurrence its traced steps consumed; for a mixture or a shard, every occurrence it holds);
- (b) each link's evidence level, stored per (occurrence, requested source) pair, can decide the request under the table in 3.2; one observed link to source A never masks a file-level link to source B;
- (c) every parent named by an edge exists;
- (d) every map's digest and record count match the artifact it describes;
- (e) for a checkpoint, every step in its history, ancestors included, has a complete trace: the step's trace counts as many samples as that step's batch size (the global batch size, or the value the registered batch schedule gives for that step), so the traces of a history sum, over its completed steps, to each step's batch size, and none of its samples has an uncovered token range (3.5); a step whose trace is missing or has an uncovered range is untraced, while a present trace whose own consumed-sample count disagrees with its step's batch size is a loud fault (3.4);
- (f) each map's stored label agrees with its stored derivation mode and verification result (3.4): a link derived by document position or token matching can carry only "recovered", "candidates" or "unknown", and counts only after its verification passed (3.3); a map whose label is stronger than its derivation allows fails the condition;
- (g) for a source that a generation edge in the ancestry does not name (for a checkpoint, the ancestry of the records its steps consumed), that edge's upper bound is established, read from the edge's stored harness log, which lists no record outside the edge's input scope, and never from a publisher's pointer or a bound field alone (3.3, Decision 13); a source an edge names only in scope gives "may contain" for that source (3.3, Decision 25). A job's own list does not establish a bound. The proof lists the edges whose bound it rests on (L8);
- (h), applied only when the generating-model extension is on (1.4) [beyond the statement; the question it lets the tool answer: can a record generated by an exposed model carry content from a source the model saw?]: for a source that edge does not name, that edge's generating model, read from its harness log and never from the job's own statement, is "none" (the log shows no model call) or a checkpoint registered in the store whose own answer for the source is "does not contain"; an output whose generating model is unregistered, is missing from the log, or answers "contains" or "may contain" gets "may contain" naming the generating model (or, where the log has no model entry, the job and the missing model entry), and never "contains" on that basis (3.3, Decision 28). While the extension is off, condition (h) is not applied: the model is a logged attribute of the edge and not an ancestor, and a negative that passes a generation edge rests on (a) to (g) and carries the words "generating-model exposure not assessed" (3.3).

A proof is needed only where absence is claimed. A recorded chain showing "contains" wins over a failed condition elsewhere, for a mixture, a shard or a checkpoint alike (2.4, Decision 20). Where no chain shows "contains", any failed condition gives "may contain" naming the first failing link, or "not covered" when the artifact's own record is missing or unregistered (2.1). Separately, four faults stop the query loudly and print no answer, whatever the answer would have been (3.4): a map whose count or digest does not match its artifact (d), an edge whose parent occurrence is absent (c), a present trace whose consumed-sample count is wrong (e), and an artifact whose digest no longer matches its file. A precomputed index may speed the walk but is rebuildable from the store and is never the authority (Decision 1).

**2.3 Requests.**
- **Withdraw a source** (Decision 24) [the request's own case]: a source is a named set of registered members, each a revision or a part of one (a file, a folder or a list of records): QA-base before and after 16 Jul 2026 are two revisions of one source, and GPQA is registered as its GPQA folders in the QA-base revision before 16 Jul 2026, which held them [CHECKED: Part 2, "The incident": each benchmark sat in its own folder, and the cleanup commit of 16 Jul 2026 removed files inside the four benchmark folders]. The records in those folders are the source's own records, and which GPQA item each paraphrase or translation among them came from stays unknown (L1). The selector names the source (every member registered under it when the query runs; the answer lists the members it expanded to) or specific members, and may narrow to a file, a folder or a list of records. A withdrawal that names a source with no registered member is refused with the named error "source not registered" and answers nothing, never "does not contain". Everything whose evidence chain requires the source is in scope. The grouping of members under a source is the team's registration; an ingested revision the team did not group under the source is outside the withdrawal, and the answer lists the members it expanded to so the team can see the gap. An occurrence in an artifact whose chain does not end at an ingested revision (it came through an input the team never registered) fails condition 2.2(a) at that occurrence, so the artifact answers "may contain" naming the occurrence and its missing origin, and is never "does not contain" while one of its occurrences has no recorded origin. Every record of a registered artifact, in a JSONL release as in a tokenized shard, is an occurrence written under that count-and-digest rule (3.4, 2.2(d)), so no record of a registered artifact is invisible to the proof; an artifact with no such map or occurrence record is "not covered" (2.1). A "does not contain" is therefore scoped to the members registered under the source, and the same content arriving through an input registered under another source lies outside the withdrawal and is found only by a content ban, when that extension is on (L2, L12). A record whose parent mode is "any" keeps its place while an equivalent parent remains; the history keeps its original attribution.
- **Ban a content across origins** [beyond the statement; the question it lets the tool answer: is this text, equal after the pipeline's normalisation (3.1), from whatever origin, in any artifact, and what is recorded as derived from it?]. A text is matched by fingerprint, plus everything recorded as derived from any match. Limit L2. Its answers are the four answers of 2.1: "does not contain" only by the proof of 2.2 over every occurrence of the artifact, so a successor shard is clean of a banned text only when its map is whole and holds no match; its rebuild is the withdrawal of the matched occurrences and of what derives from them, under the actions of 4.1; the first build sets no repair check for it (1.4). While the extension is off the request is refused with a named error (L7).
- **Start from flagged records** [beyond the statement; the question it lets the tool answer: given a scanner's or an allowlist's output, which roots and which siblings are implicated?]. Trace back to roots, forward to every sibling, then answer as a withdrawal of those roots. While the extension is off the request is refused with a named error (L7).
- **Unsupported requests.** A selector the first build does not support (a metadata prefix such as a URL prefix), a request of an extension that is off (1.4) or a corpus format it does not read (anything but JSONL and Megatron binary shards) is refused with a named error before any answer; the tool never approximates it (L7).

**2.4 Checkpoints (Decisions 12 and 20).** The tool distinguishes three levels of evidence: eligible (the record was in a mixture the run used), consumed (read by a completed step, with the first such step) and inherited (an ancestor checkpoint was exposed).
- "contains" when an affected record is shown consumed in the checkpoint's history (a trace row of a completed step inside the covered part of a sample, 3.5, on a version for which Check 1 has verified F9; on an unverified version, an unverified sampler type or, for a cyclic run, a shuffle with no matching recorded digest, the answer is "may contain", F6, 3.5) [BUILD COPY: M4; R5], or an ancestor answers "contains" (its basis passes down); the answer states its basis, "whole-sample read assumed (F9, L9)" (where an operator note covers the sample, the note is the basis), because Check 1 verifies F9 for a version and the tool cannot show that this run's trainer read every sample in full; this holds whatever else in the history is untraced, and the answer lists the untraced steps beside the chain;
- "does not contain" when every step of its history is completely traced (2.2(e)) on a version and sampler type for which Check 1 has verified F9 and, for a cyclic run, with the join's shuffle matching the recorded digest (3.5) [BUILD COPY: R5; M4], the rest of the proof of 2.2 holds over the records its steps consumed, and none read an affected record, even if one was in its mixture;
- "may contain" when it does not "contain" and some step of its history is untraced (the answer names the missing trace, whether or not an affected record was eligible in that step, because the tool cannot show the step read none), or a record its steps consumed fails a condition of the proof of 2.2 (the answer names the condition and the record), or the Megatron version is unverified (F6; the answer names "data-order trace unverified for this version"), or the run's sampler type is one Check 1 did not verify (F6; the answer names "data-order trace unverified for this sampler type") [BUILD COPY: M4], or, for a run read with the cyclic sampler, the shuffle the join computes has no matching digest in the run record (3.5; the answer names "cyclic order not recorded" or "cyclic order digest mismatch") [BUILD COPY: R5], or an ancestor answers "may contain";
- "not covered" when the checkpoint's own record, its run segment, is missing or the checkpoint was never registered (2.1).

A record counts as consumed when any of its tokens is read (Decision 18). Negative answers are scoped to the source, run and steps covered and, past a generation edge, to the reads its harness log shows (L8) and, with the generating-model extension on, to the model it shows (L11), and to the inputs registered under the source (L12). Exposure counts (an extension, off in the proposed first build, 1.4), how many times each affected record was read up to each checkpoint, are reported with their condition: a count is a lower bound only where no counted sample may have been partly read (F9 holds for the run, which Check 1 verifies for the version only and the tool assumes for the run, L9; or an operator note covers every partial read); an untraced step can only make a count too low and an unnoted partial read can only make it too high (L9), so where both can hold the count is an estimate with no bound in either direction, and the report says which of the three it is; no "does not contain" is ever derived from a count [beyond the statement; the question it lets the tool answer: how heavily was a checkpoint exposed to an affected record?] While the extension is off, the report gives each checkpoint's steps and first exposure and no count.

## 3. What is recorded

**3.1 Records.**
- **Source revision:** an input pinned by digest. QA-base before and after 16 Jul 2026 are two revisions [CHECKED: Part 2, "The incident"]. A **source** is a named set of registered members, each a revision or a part of one (2.3).
- **Artifact instance:** a registered artifact, identified by its content digest together with its history: the instance id is a hash of the content digest, the name, version and parameter digest of the step that made the artifact, the instance ids of that step's input artifacts in order and the digest of the artifact's own edge records, each record written as (the child's locator inside the artifact, the instance ids and locators of its parents, and, for an "any" edge, the instance id and locator of the parent the step selected, in a field of its own, so that two histories that differ only in which equivalent parent dedup kept give different edge digests and so different instance ids) [BUILD COPY: A1]; for an ingested source revision, of its content digest and the member name it is registered under. The construction has no cycle: a child is named in the edge digest by its locator alone and never by an occurrence key, so the digest does not contain the artifact's own instance id; the parents' instance ids are those of artifacts that existed before this one, and a parent in the same artifact is named by its locator alone; and the order is fixed: the content digest, then the edge digest, then the instance id, and only then are the occurrences keyed (instance id plus locator) and the edges stored under those keys. Two artifacts with identical bytes made by different histories (a release whose X came from A and a release with the same bytes whose X came from B) are two instances; one artifact registered twice with the same history is one instance (Decision 29). The digest conditions (2.2(d), the loud checks of 3.4) stay on the content digest.
- **Occurrence:** a record at a place: the artifact instance plus a locator (file and line in JSONL, ordinal in a tokenized shard). Document 17 of one shard and document 17 of another are different occurrences, and so are document 17 of two instances with identical bytes.
- **Fingerprint (Decision 11):** a 128-bit hash (BLAKE2b with a 16-byte digest) of a record's text after one fixed normalisation, the pipeline's own sanitizer where it has one. Equal fingerprints mean equal after that normalisation, not necessarily equal raw bytes and not the same origin. Recovery attaches a record to a unique candidate only after the tool reads both records and compares their normalised texts directly, which rejects a hash collision; a content ban reports its matches as "equal after normalisation" and lists the occurrences so a team can compare raw text. The chance of any collision among n records is about n squared over 2 to the 129th power, about 1.5 in 10 to the 21st at 10 to the 9th records (birthday bound, derived here).
- **Edge:** a child occurrence and its parent occurrences, with the transform's name, version and parameter digest, a parent mode, an evidence label and, for a generation edge, its harness log (the records the job read and the model it called, or that it called none, with the log's digest), from which the edge's upper bound is derived (established only when the stored log lists no record outside the edge's input scope; a mapped edge has no log and no established bound; a bound field edited to say otherwise is caught as 2.2(g) states), and, for each record handed to the job, whether the output used it. A parent of a generated output is a record the output used (the sole input, or one the output states it used); a record handed to the job and not stated as used is in scope only and is not a parent (Section 10). Parent mode "all" means every parent was used (a summary of A and C); "any" means the parents are equivalent copies and one was selected (dedup kept A's copy of a passage B also supplies). Labels are in 3.2.
- **Drop:** an occurrence a step removed, with the reason (sanitizer skip, filter, dedup loser), so a rebuild can tell what returns when a winner is withdrawn.
- **Artifacts and runs:** each artifact's digest, producing step and inputs; a mixture snapshot (the exact shard files and settings the trainer used); a run segment (mixture snapshot, data-order settings and seed, with the sampler type, the `data_sharding` flag, the micro batch size, the world size of each launch, the train state at each start, the ordered shard list, the `add_extra_token_to_sequence` flag and the versions of Megatron-core, Megatron-Bridge and torch [BUILD COPY: M3], the digests of its index cache files, read from the run record the training wrapper wrote while the caches existed (3.3, Training), and, for a cyclic run, the digest of each epoch's shuffle from the same run record (3.5) [BUILD COPY: R5], completed steps with, per step, the samples consumed and, only where the operator supplies it, how many tokens of the step's last sample were read, parent checkpoint; a note can only lower a step's coverage, never raise it, so it can turn a "does not contain", or a "contains" that rests on the unread part, into "may contain" and never the reverse); a step trace per completed step (3.5); a checkpoint (run segment, step, parents). **[beyond the statement; an extension, off in the proposed first build, 1.4]** Published models made from a checkpoint, post-trained or quantized, are recorded as its children, and a published model answers as its parent checkpoint does, carried down the link; the question this lets the tool answer: which published models carry exposure? soofi's hub lists post-trained previews and quantized variants [CHECKED: Part 2, "The incident"]. While the extension is off a published model is not registered, and a query naming it answers "not covered", "not registered" (2.1).
- **Storage:** locators, fingerprints and edges, never record text; every map also stores its derivation mode and verification result (3.4).

The principle: keep the least evidence that still justifies a specific repair and checkpoint decision months later. Each irreversible step (an unseeded shuffle, a generation job, tokenization) is the last cheap chance to record its link.

**3.2 Evidence labels and what each can decide.** The store derives which labels a link may carry from how it was derived (3.4); a tokenization link can never be "observed".

**3.3 How each step's link is obtained.** The tool wraps the team's existing steps; it does not replace their pipeline, scheduler, tokenizer or trainer.
- **Ingest** (listing the JSONL): observed. Pin revisions, digest files, record occurrences and fingerprints.
- **Copy steps** (shuffle, chunk, merge): observed by a thin wrapper, or recovered by fingerprint. Identical texts from different origins give a set of candidate parents, so such a record is "may contain" for a source withdrawal unless the step was observed (L3).
- **Deterministic rewrite** (sanitize): recovered by re-running the same function before matching; skipped and empty lines are read from the step's own log as drops. If the function or its version is unavailable, the link degrades to file-level or unknown (F8).
- **Generation** (paraphrase, translation, synthesis): observed (the wrapper runs the job in a closed-input harness: the job is handed its input records and can reach no other record or record source, and the harness's access log lists every record it read; the wrapper writes the output's parent references from the records the output used, the sole input or each input the output states it used, in a field of each output record or in a side file, and lists a handed input the output does not state as in scope only; a job may instead write its own list, observed for the parents it names, with nothing established about what else it read), mapped where a publisher's pointer is verified on the data, otherwise file-level or unknown. The tool checks that each named parent exists and lies inside the job's input scope. Two things are kept apart. The upper bound, that the job read nothing outside the listed records, is established when the access log lists no record beyond the handed ones; otherwise it is not established. For a mapped edge it is never established: a publisher's pointer names the source an output was made from and shows nothing about what else the job read (Decision 13). The exact parent is a listed record that the output used. So for a source the edge does not name, "does not contain" needs an established bound and otherwise the answer is "may contain" naming the job (condition 2.2(g)); a source named only in scope gives "may contain", never "contains" (3.2, Decision 25). The harness log also records the model the job called, or that it called none, for every generation edge; it is read from the log and never from the job's own statement. The generating-model rule ([beyond the statement; an extension, off in the proposed first build, 1.4; the question it lets the tool answer: can a record generated by an exposed model carry content from a source the model saw?]) uses it as follows when the owner switches it on. The model is a recorded input of every output (a log with no model entry is read as "not established", never as "no model", and the answer names the job and the missing model entry). A generating model that is a registered checkpoint of the store is an ancestor of its outputs in the walk, so the tool answers for it as for any checkpoint (2.4); one that is not registered is "not covered", so its outputs answer "may contain" naming it (2.1). For a source its edge does not name (2.2(h)), an output of a generating model that answers "contains" or "may contain" answers "may contain" and not "contains" [BUILD COPY: A4: an output with a confirmed affected record among its own parents keeps "contains" through that chain, 2.2, Decision 20]: the tool records that the generating model was exposed to the source, not that this output carries any of it, whereas a checkpoint that descends from an exposed checkpoint holds the exposed weights (2.4). Where a publisher's pointer is the only evidence, the generating model is not registered, so (h) cannot be met and the outputs of a mapped edge never reach a negative for a source the edge does not name; they answer "may contain" naming the model as unregistered. While the rule is off, the model is only a logged attribute of the edge: it is not an ancestor in the walk, condition (h) is not applied, and a negative that passes a generation edge rests on conditions (a) to (g) and carries the words "generating-model exposure not assessed"; the tool can then give "does not contain" for a record that a model exposed to the source generated, which Section 7 puts to the owner. A parent is never recovered by similarity; a similar string or matching row number is listed as a lead outside the answer (L5).
- **Selection** (dedup): observed. The group of equivalent occurrences, the survivor and the losers (parent mode "any"). soofi deduplicated upstream, so its losers never reach the tool [CHECKED: Part 2, "soofi's published pipeline"].
- **Tokenization (DEEPSEEKV41FLASH-2, deepseek-v4.1-flash).** The wrapper runs the team's tokenizer unchanged as an external subprocess and writes a companion map per shard in its own namespace: ordinal, occurrence, fingerprint, token start and token end, modelled on Dolma's per-document rows [CHECKED: Part 2, "Existing tools"]. Megatron's preprocessing keeps only the text field and the index file stores document boundaries only, so the ordinal-to-occurrence link is derived, never observed [CHECKED: Part 2, "soofi's published pipeline"]. There are two derivation modes, and the order is fixed:
  - *Position mode* runs first (it needs F1): count surviving input lines in order and give each the next ordinal, a line that gives no tokens counted as a drop and the `--append-eod` setting recorded (F1) [BUILD COPY: M11]. The wrapper uses it at tokenization time, when the chunk files still hold their ids (where F1 is disproved the wrapper uses token-matching mode instead). Recovery for a run made without the wrapper uses it over the surviving lines, reading sanitizer skips and empty lines from the sanitizer's log as drops so ordinals do not shift. A document whose tokens equal another document's in the same shard (an identical twin) is labelled "candidates", with the twins' occurrences as its candidate set, because no verification can show which twin sits at which ordinal; verification catches any displaced content-distinct document, so only a swap within twins can escape it, and for them the label already says the link is not known. Twins in different shards are told apart by their shard. Check 3 tests this against the ids the replica's chunk files carry up to the tokenizer.
  - *Token-matching mode* takes over for a run when position mode's verification fails or F1 is disproved for it: match each document's tokens to a re-tokenization of the input lines. Identical documents give a set of candidate parents of size two or more, labelled "candidates".
  Every map stores its derivation mode, its verification result (passed, failed or not run) and its label. Verification runs for both modes: each ordinal's token span equals the shard's own recorded size; in position mode the document count equals the surviving input-line count; and each document's tokens match a re-tokenization of its line. The label follows from the mode and the result: passed gives "recovered" for a document whose tokens equal no other document's in its shard and "candidates" (the twins' occurrences) for the rest; failed or not run gives "unknown". Token matching is run on every document in the first build and its cost is measured (5.6); whether a sample suffices at scale is unknown (risk RK3). A recovery map is written to a separate namespace so a wrapper-written map is never overwritten. The end-of-document convention (whether that token lies inside a document's span) is read from the oracle's output on the hand-checked fixture and recorded in the fixture spec before Check 3 runs (F1).

**3.4 The evidence store (DEEPSEEKV41FLASH-1, deepseek-v4.1-flash).** One SQLite file holds sources, occurrences, fingerprints, edges (with each generation edge's harness log), drops, artifacts, runs, step traces, checkpoints and map bindings, and is the only writer of them. It runs with write-ahead logging and full synchronous writes; the schema is versioned and migrated stepwise.
- `store.write_map()` is one transaction and refuses unless the declared record count and artifact digest match the artifact on disk; the occurrences of a JSONL artifact (a source file or a release) are written in one transaction under the same rule, with the declared line count and the file's digest checked against the file. A map record stores its derivation mode, its verification result and its label, and the store refuses a label stronger than the derivation allows; a label edited after writing is caught by condition 2.2(f).
- Four checks stop the query with a named error and a nonzero exit code and print no answer: a map whose count or digest does not match its artifact; an edge whose parent occurrence is absent; a present trace whose consumed-sample count differs from its step's batch size (the global batch size, or the value the registered batch schedule gives for that step, so that a history's counts no longer sum to its steps' batch sizes; implemented once, here; condition 2.2(e) calls it; a missing or partial trace is not a count fault but an untraced step, and a gap in a trace never touches a shard map, since a map that exists is whole); an artifact whose digest no longer matches its file.
- Coverage is computed on demand from these tables; no second per-artifact ledger is written, so edges and maps cannot disagree after a crash (Decision 2).
- The store's size and speed at scale are unknown (risk RK3).

## 4. The rebuild (SONNET55-3, sonnet5.5, with DEEPSEEKV41FLASH-3)

**4.1 The rebuild report.** For every affected artifact the report gives its revision, the reason (the evidence chain) and one action:
- **keep**: no ancestor is in scope.
- **rewrite**: the artifact is rebuilt without the affected occurrences (a shard re-tokenized).
- **re-source**: an "any"-parent record whose chosen parent is withdrawn takes an equivalent parent that remains; the successor release row is re-sourced and the history keeps the original attribution.
- **promote**: the dedup loser whose winner is withdrawn returns to the release. Re-source and promote are the two rows of one event: for passage X under "withdraw A", the release row is re-sourced to B's copy and B's copy is promoted.
- **retire** (Decision 10): a descendant is removed from the successor when any parent of an "all" edge is in scope, or every parent of an "any" edge is. A summary of A and C with A withdrawn alone is retired. Regenerating a retired record is the team's follow-on step; the report names its generation step and parameter digest so the team can rerun it.

A record whose answer for the withdrawn source is "may contain" has no action: the report lists it as unresolved with the missing link (for a record generated by a model, with the generating-model extension on, the generating model or the missing model entry, 2.2(h)), and a successor that holds it answers "may contain" for the source until the team resolves it (4.4). The report counts records removed and bytes to rewrite, and shards rewritten per layout. ## 6. Limits, framework assumptions and risks

**Limits (what the design cannot know, and what the tool answers).**
- L1. A derivation that was never recorded, as with a text-only import like QA-base [CHECKED: Part 2, "The incident"]: the tool cannot know which item a record came from; it answers at the recorded level ("this file holds GPQA-derived items") and marks individual records "may contain".
- L2. A content ban (an extension, 1.4) finds whole records equal after normalisation only. A passage inside a longer document, or a near copy, is found only through recorded edges or through a search index's matches fed in as flagged records; otherwise the tool answers "may contain" and says the passage was not matched.
- L3. Identical texts from different origins at an unobserved copy step: a set of candidate parents; "may contain" for each candidate's source.
- L4. No model is trained, so the first build can show nothing about weights; the tool reports exposure and restart points and verifies data rebuilds.
- L5. A generation's parent is never recovered by similarity; leads are listed outside the answer, and the record's answer stays file-level or "may contain".
- L6. What was in a training directory at training time, if no mixture snapshot was recorded: the mixture is "not covered" (its own record is missing, or it was never registered, 2.1) and the run's checkpoints answer "may contain", naming the missing snapshot. A past run trained through Megatron-Bridge does hold its shard list, by path and without digests, in each checkpoint's saved config; it pins no content, so under these rules it is a weak link and the checkpoints' answers stay "may contain" [BUILD COPY: M16].
- L7. A selector or format the first build does not support, or a request of an extension that is off (1.4), cannot be answered: the tool refuses the request with a named error and gives no approximate answer (2.3).
- L8. A generation job that is not run in the closed-input harness, whose access log lists a record beyond the handed ones, or a mapped edge, whose publisher's pointer does not show what the job read: the tool cannot know what else the job read. It answers "may contain" naming the job for every source the edge does not name. Where the bound is established, a "does not contain" is scoped to the reads the harness log shows, and the proof lists the log entries it rests on; what the job's model learned is handled by the generating-model rule when it is on (L11).
- L9. F9 is an assumption about the trainer. Where it is wrong for a team's run (the trainer read only part of a step's last sample and no operator note says so), the tool cannot know: it counts the sample whole, so a "contains" or an exposure count can reach a record in the unread part, an over-report that never produces a "does not contain" (the tokens the join resolves for the sample include everything the step read, which holds because the join resolves each sample's sequence_length + 1 tokens, 3.5) [BUILD COPY: M9], and the count is not a lower bound unless an operator note covers every partial read (2.4). Check 1 verifies F9 for a version against the oracle's log, and where the join's version was not verified (F6) the checkpoint answers "may contain" naming "data-order trace unverified for this version", so no "contains" rests on an F9 that is unverified for the version; for a verified version it rests on the run's whole-sample read assumed, which the answer states (2.4). A skipped iteration counts as read, since on Megatron-Bridge's path the samples of a skipped iteration count as consumed: an over-report in the same direction [BUILD COPY: M17].
- L10. An artifact never registered and never named by any record: the tool cannot know it exists. A listing states what it covers, so the gap shows as the difference between that statement and the team's own inventory; asked about the artifact by name, the tool answers "not covered", "not registered" (2.1).
- L11. (Applies when the generating-model extension is on, 1.4. While it is off, the tool cannot know what source content a generating model carries; it does not ask, and its negatives past a generation edge say "generating-model exposure not assessed", 2.2(h).) A generating model with no registered history (a hosted model, or a model whose training records were not kept) or no entry in the harness log: the tool cannot know what source content it carries. Every output it generated answers "may contain" naming the generating model (or, where the log has no model entry, the job and the missing model entry), for every source the edge does not name; the answer is "does not contain" only where the generating model is "none" or a registered checkpoint that answers "does not contain" (2.2(h)). The cost is not confined to the record: an artifact is answered from its whole ancestor closure (2.2), so one such record keeps its shard, every mixture that holds the shard and every checkpoint that read it at "may contain" for every source the record's edge does not name, and where such records sit in every chunk (4.5) no shard or mixture of that phase, and no checkpoint whose consumed history includes such a record, can answer "does not contain" for such a source. Recording a generation edge therefore gives a weaker answer than importing the same rows as plain text, which is scoped to the registered members and can reach a negative (2.3, L12); the team needs the edges to ask the request's own question about a source's translations. If the model that wrote a set such as QA-base's paraphrases is not a registered checkpoint, a team that captures it gets "contains" for each paraphrase of an affected item, "may contain" for every other record of the set and an unresolved list of the set's size, with no claim that the repaired release equals a clean build (4.2), while a team that imports the same rows as plain text gets a clean answer. The fixture shows none of this: its generating models are stubs (5.1), and no check shows that a real team's models can supply a registered history.
- L12. An input never registered, or registered under another source: the tool cannot name it and cannot know that its content belongs to the withdrawn source. An occurrence whose chain ends short of an ingested revision answers "may contain" naming the occurrence and its missing origin (2.2(a)); content that arrived through an input registered under another source is outside the withdrawal, and only a content ban (L2), an extension (1.4), finds it, as "equal after normalisation" matches.

## 8. Decisions

### Decision 1: Where "does not contain" is decided
- Context: the request asks for exact answers; a missing record must never read as absence.
- Options considered: (a) each query applies the rule by convention and review; (b) a precomputed per-artifact ledger is the authority; (c) an on-demand proof from the store, behind an answer type that cannot build "does not contain" without it.
- Trade-offs: (a) is the least machinery but depends on every query remembering the rule; (b) answers fast but goes stale when a map or edge changes; (c) costs a walk of the ancestor closure per query and buys a rule that holds by construction.
- Choice: (c); a rebuildable index may speed it.
- Why the others lost: (a) leaves absence one forgotten check away; (b) can disagree with the edges it summarises.
- Consequences: the store must expose every link level per (occurrence, requested source) pair; the mutation test of Check 5 becomes the evidence. A measured walk time that is unusable on a real corpus would change the call toward an index that is verified, not trusted.

### Decision 2: The evidence store
- Context: maps, edges and run records must stay consistent after a crash and be queried by ancestry.
- Options considered: (a) one transactional SQLite file; (b) per-artifact files with a ledger file; (c) append-only JSONL with offline compaction; (d) a columnar file format per table.
- Trade-offs: (a) gives atomic cross-table writes and ancestry queries on a laptop with no server, at unknown scale; (b) is easy to diff but gives no cross-artifact atomicity; (c) is simple to write, but an ancestry query needs an index built over the log or a replay of it, which is extra indexing work and a second structure to keep in step with the log; (d) scans well and updates badly.
- Choice: (a) for the first build.
- Why the others lost: (b) lets a ledger and edges disagree after a crash; (c) adds that indexing or replay work to ancestry queries, or a second structure that must stay in step with the log; (d) cannot update a map under a binding check in one transaction.
- Consequences: Check 4 tests the kill and the four loud checks; behaviour at scale is unmeasured (risk RK3). A measured size or query time beyond a laptop budget would change the call.

### Decision 3: Evidence level granularity
- Context: a request about source B must not be decided by a strong link to source A.
- Options considered: (a) one strongest level per occurrence; (b) one level per (occurrence, requested source) pair.
- Trade-offs: (a) is smaller and answers faster; (b) stores more and never lets one source's observed link hide another's file-level link.
- Choice: (b).
- Why (a) lost: an observed link to A would let a record-level request about B reach "does not contain".
- Consequences: more rows per edge; Check 5 includes the A-observed, B-file-level case. Measured storage that proves too large would change the call toward a compact encoding of (b), not toward (a).

### Decision 4: How tokenized documents are linked to their records
- Context: Megatron's preprocessing drops ids and keeps document boundaries only, so tokenization is the last point a record still has an identity [CHECKED: Part 2, "soofi's published pipeline"].
- Options considered: (a) modify or fork the tokenizer to write ids; (b) run it unchanged and write a companion map by position, verified; (c) match every document's tokens to input lines with no position map.
- Trade-offs: (a) gives the strongest link but changes the team's step and may bring tokenizer code into the tool; (b) needs no change to the team's step, but its link is derived by position, so it carries "recovered" for a content-distinct document and "candidates" for identical twins in one shard; (c) needs no assumption about line counting and gives the same links as (b), but needs the team's tokenizer reproduced exactly whenever the link is rebuilt, which can fail for a run recovered months later.
- Choice: (b) in position mode, with (c) as its verifier (it catches any displaced content-distinct document), as the recovery mode for a run made without the wrapper when position mode's verification fails, and as the wrapper's own mode where F1 is disproved (3.3).
- Why the others lost: (a) puts third-party code into the tool under an unsettled licence reading; (c) alone depends on reproducing the tokenizer at every rebuild, while position mode depends only on F1 and still has (c) as its check while the tokenizer is at hand.
- Consequences: the map stores its derivation mode, verification result and label, counts only after verification (2.2(f), Check 3), and labels identical twins "candidates" in every mode; F1 is the assumption behind it. A tokenizer that writes ids would change the call toward observed maps, which would also separate twins.

### Decision 5: The exposure join and its oracle
- Context: every checkpoint answer rests on mapping steps to shard positions, and the join's expected answer must not come from the join.
- Options considered: (a) a join from the cache files' documented semantics, judged against Megatron's own code run at test time; (b) a join that vendors Megatron's sampler code; (c) a join judged only against hand-written tables.
- Trade-offs: (a) keeps the shipped tool free of Megatron code and gets an expected answer from the trainer's code, at the cost of a test-time dependency; (b) matches the trainer exactly but ships code under a licence recorded inconsistently [CHECKED: Part 2, "Existing tools"]; (c) needs no dependency but tests the reading against the reader's own beliefs.
- Choice: (a).
- Why the others lost: (b) carries an open licence question into the tool; (c) cannot find a wrong reading of an index file.
- Consequences: F5 and F6 apply; the golden-log fallback exists. A settled licence reading would lift the no-vendoring default. [BUILD COPY: M12: for a run trained through Megatron-Bridge the oracle runs Megatron-Bridge's own sampler file (F5); Megatron-Bridge is Apache-2.0, so for that file the licence reason against (b) does not hold, and (a) stands on W5: a join graded by the code it runs could not come out the other way (1.3)]

### Decision 6: Successor shape
- Context: after a withdrawal the successor release either shrinks or refills.
- Options considered: (a) shrink: removed tokens are not refilled; (b) refill to the original token budget.
- Trade-offs: (a) makes the successor's record multiset equal to what a from-scratch run without the withdrawn content retains, a reference built with no further choice; (b) keeps the trainer's token budget but needs a refill policy (which records fill the gap, from which sources, in what order) that the original pipeline never defined, so the reference becomes a from-scratch run under that new policy and every repair check depends on the policy as well as on the withdrawal.
- Choice: (a).
- Why (b) lost: the first build would have to design and verify a refill policy as well as the repair, and the successor would hold records the original release did not hold; a deterministic policy run from scratch on clean inputs could serve as a reference, and a team that needs a fixed budget builds that on its own side (Consequences).
- Consequences: Check 9's multiset equality; a team that needs a fixed budget refills on its own side and reruns the tool's verification on the result. A trainer that cannot take a smaller release would change the call.

### Decision 7: Wrap the team's steps, or recover afterwards only
- Context: the request starts from a pipeline the team already has, and links lost at irreversible steps cannot be recovered later.
- Options considered: (a) recovery only, with no wrapper; (b) thin wrappers that capture where the step allows it and recovery as the fallback; (c) a replacement pipeline framework that records everything.
- Trade-offs: (a) touches nothing but leaves candidate sets wherever copies repeat; (b) asks a team to run its generation jobs in the closed-input harness and to make small changes at selection, tokenization and mixture selection, and still serves teams that never installed it; (c) gives complete records but asks a team to adopt a new pipeline.
- Choice: (b).
- Why the others lost: (a) cannot give exact answers across a generation step; (c) is not the first target, which is soofi's existing shape [CHECKED: Part 1, "What we want"].
- Consequences: the measured items include lines changed to wire capture into one generation step; if that count is large, the call moves toward (a) for that step.

### Decision 8: The answer vocabulary
- Context: the request asks for exact answers while recorded evidence is often incomplete; the vocabulary decides what a team can act on.
- Options considered: (a) four typed answers (contains, may contain, does not contain, not covered); (b) three answers, with a shard that has no record reported as "may contain"; (c) a binary answer with a confidence score.
- Trade-offs: (a) separates "records exist but are incomplete" from "no records", which tells a team where to install capture, at the cost of one more state; (b) is simpler but hides a missing artifact among partly recorded ones; (c) invites a reader to round a high score into absence.
- Choice: (a), with the own-record boundary of Decision 21.
- Why the others lost: (b) cannot tell an uninstalled pipeline from an incomplete one; (c) turns absence into a number.
- Consequences: Check 5 tests the boundary between "may contain" and "not covered", and the unregistered case. Evidence that teams never act on the difference would change the call toward (b).

### Decision 9: Where the store and its fingerprints live
- Context: fingerprints let anyone holding a text test whether it is in a corpus, and the store maps a team's restricted corpus.
- Options considered: (a) a local store on the team's own machines; (b) a hosted shared registry; (c) keyed fingerprints, under a team secret, in a shared store.
- Trade-offs: (a) leaks nothing and works offline, but gives no cross-team view; (b) gives cross-team lineage and one backup but moves records of restricted text to a host; (c) lets teams share without outside membership tests but needs key custody and loses every match if the key is lost.
- Choice: (a).
- Why the others lost: (b) exposes which texts a team holds to a third party; (c) adds key custody and a single point of loss.
- Consequences: W1; the first build needs no server. Teams that share corpora and want joint lineage would change the call toward (c).

### Decision 10: Rebuild actions for descendants
- Context: the request asks what must be rebuilt; translations, paraphrases and summaries of a withdrawn source need an action, and some descendants cannot be shown to derive from it.
- Options considered: (a) retire a descendant shown to derive from the source, leave regeneration to the team, and list a descendant whose answer is "may contain" as unresolved; (b) regenerate descendants inside the tool by rerunning the recorded transform; (c) keep descendants and flag them for review; (d) retire every descendant whose answer is "may contain" as well.
- Trade-offs: (a) keeps the tool's output checkable against a from-scratch run, leaves model calls with the team, and removes only what is shown to derive; (b) closes the loop but needs the tool to call generation models, whose code and versions an edge's parameter digest does not carry; (c) leaves derived content of a withdrawn source in the release; (d) leaves no unresolved record but removes content that may not derive from the source, so the successor can differ from a from-scratch run without the source.
- Choice: (a).
- Why the others lost: (b) needs a reproducibility record of the job (its code, model version, parameters and inputs) that an edge's parameter digest does not carry, so the tool cannot rerun the job faithfully; (c) defeats the removal the request asks for; (d) breaks the equality that Decision 6 relies on for records that were never shown to derive.
- Consequences: "retire" is the one action for a shown descendant (4.1) and the report lists the undecided ones as unresolved with their missing link, and, with the generating-model extension on, a record generated by an exposed or unregistered model among them (2.2(h)); a team that regenerates reruns the tool's verification on the result. A team that prefers over-removal to review would change the call toward (d); edges that carry full reproducibility records for a job would make (b) a real option.

### Decision 11: The fingerprint
- Context: occurrences are matched by fingerprint in recovery and in content bans, and text is never stored.
- Options considered: (a) a 128-bit hash of the normalised text, with a direct comparison at recovery time; (b) a pair: a hash of the normalised text and a hash of the raw bytes; (c) a 256-bit hash of the normalised text.
- Trade-offs: (a) costs 16 bytes per record, and equality means equal after normalisation; (b) separates raw-different records at double the per-record bytes; (c) lowers collision odds below what the corpus size needs at 32 bytes per record.
- Choice: (a).
- Why the others lost: (b) the pipeline's own sanitizer already makes normalised-equal records the same record downstream; (c) the collision chance at 10 to the 9th records is already about 1.5 in 10 to the 21st (3.1).
- Consequences: metadata bytes per record are measured (5.6). A sanitizer whose normalisation merges records that matter would change the call toward (b).

### Decision 12: The checkpoint trace rule
- Context: an untraced step could have read an affected record, and a mixture snapshot says what it could have read.
- Options considered: (a) any untraced step in a checkpoint's history gives "may contain"; (b) a run segment whose mixture snapshot holds no affected record needs no trace, because reads are a subset of the mixture.
- Trade-offs: (a) never answers "does not contain" without a trace for every step, at the cost of "may contain" for clean early segments when data-order files are lost; (b) keeps those answers exact but lets a wrong or recovered snapshot produce a false "does not contain".
- Choice: (a).
- Why (b) lost: a snapshot is a record like any other, so its error would pass the proof silently.
- Consequences: Check 2's expected answers (all four checkpoints "may contain" when the data order is lost) and Check 5's deleted-trace fault. A snapshot taken when training starts and checked against the shard files' digests (Decision 27) shows what the directory held then and not which files the steps opened, so it does not meet this condition; (b) would become acceptable only with a log of the shard files the trainer opened during the run, which the first build does not capture. [BUILD COPY: F-4: advisory, from Fable's second review: Decision 27 describes the same snapshot as letting a later query say which shards a run could have read, which is all option (b) asks for, so this reason does not follow from that description; the choice (a) and its stated price stand, and no answer changes]

### Decision 13: When a generation edge's parent list can support "does not contain"
- Context: a job can read beyond what it lists, and a negative about a source the edge does not name needs an upper bound on what the job read.
- Options considered: (a) a bound is established only by the tool: a closed-input harness whose access log lists every record the job read, and otherwise the answer is "may contain" naming the job; (b) accept the job's own list as the bound; (c) accept the list the wrapper wrote from what it handed the job, with no restriction on the job; (d) check completeness by similarity or by rerunning the job; (e) accept a publisher's pointer, verified one-to-one on the data, as the bound.
- Trade-offs: (a) lets absence rest on a record the tool's harness produced, at the cost of "may contain" for jobs that cannot run in the harness, such as a hosted job with its own retrieval; (b) answers more questions exactly but lets the job's own claim authorise absence, the error Decision 12 rejects for snapshots; (c) records what the job was given and not what it read, so a job that read more still yields a negative the tool cannot support; (d) would not depend on the job but can never be exact, and inside an exact answer it would hide which hits are guesses; (e) names the source an output was made from, not what else the job read, so it would let a publisher's claim authorise absence, the error of (b).
- Choice: (a), with the log entries a proof rests on listed in the proof (L8).
- Why the others lost: (b) lets an unverifiable claim decide absence; (c) mistakes a hand-off for a read log; (d) is excluded by the rule that a parent is never recovered by similarity (L5); (e) is the same unverifiable claim as (b), made by a publisher instead of a job.
- Consequences: F10; Check 5 includes faults that remove the established bound; a hosted job whose provider logs every retrieval it makes, checked by the tool against the parent list, would let a job outside the harness establish a bound and change the call. What the job's model learned is a separate question, settled by Decision 28; a mapped edge has no established bound, so its outputs never reach a negative for a source the edge does not name (3.3, 2.2(g)), and with the generating-model extension on it has no registered generating model either (2.2(h)).

### Decision 14: The set of evidence labels
- Context: each link must say how strongly it decides a request, so that "does not contain" cannot rest on a weak link.
- Options considered: (a) the labels of 3.2 (observed, mapped, recovered, candidates, file-level, unknown); (b) one numeric strength per link; (c) two labels, recorded and unrecorded.
- Trade-offs: (a) names the granularity each label can decide and how the link was derived, at the cost of six states to maintain; (b) is compact but cannot say that a strong link decides a whole-file request and not a record request; (c) cannot separate a derivation by rule from one the step stated.
- Choice: (a).
- Why the others lost: (b) hides which requests a link can decide; (c) lets a position-derived link count as much as a stated one.
- Consequences: 2.2(b) and 2.2(f) test labels against requests and derivations; Check 5 includes the label faults. A pipeline that records only one kind of link would change the call toward fewer labels.

### Decision 15: Parent modes and an "any" row whose parent is withdrawn
- Context: a summary needs all its parents, a dedup survivor needs only one of equivalent copies, and a withdrawal treats the two differently.
- Options considered: (a) a parent mode "all" or "any" on every edge, and for an "any" row whose chosen parent is withdrawn, re-source it to a remaining equivalent and promote the dedup loser; (b) the same modes, but drop the row and let the release shrink; (c) no modes, with every multi-parent edge treated as "all".
- Trade-offs: (a) keeps passages that another source independently supplies, so the successor equals a run without the withdrawn source (4.2); (b) removes content the remaining sources still supply, so the successor differs from that run; (c) retires a dedup survivor that a remaining copy could keep.
- Choice: (a).
- Why the others lost: (b) breaks the multiset equality that Check 9 relies on (Decision 6); (c) cannot tell a summary from a survivor and so over-retires.
- Consequences: Checks 7 and 9 test X (re-source and promote) and S (retire). Evidence that withdrawals in practice must also remove copies that other sources supply independently would change the call toward (b); a policy that one passage must leave every source is a content ban (2.3), not a withdrawal.

### Decision 16: The unit of accounting
- Context: the request asks which records a successor keeps or takes from elsewhere, so the unit the tool records decides which questions it can answer at all.
- Options considered: (a) the occurrence: a record at a place, with edges between occurrences; (b) file-level lineage: each file's set of sources; (c) run-level lineage: which sources fed which mixture and checkpoint.
- Trade-offs: (a) answers keep, re-source, promote and retire per record and gives a per-item "does not contain" inside a file, at the cost of metadata per record and slower queries; (b) holds far less metadata and answers which files to rewrite, but cannot say which records of an affected file a successor keeps, so it rewrites or retires whole files; (c) is the smallest and says which mixtures and checkpoints are affected, but nothing about what to rebuild inside them.
- Choice: (a), with file-level kept as an evidence label (3.2) wherever only file-level evidence exists.
- Why the others lost: (b) cannot answer "which records the successor keeps or takes from elsewhere"; (c) cannot answer "what must be rebuilt".
- Consequences: metadata bytes per record and per link are measured (5.6); a measured size or query time beyond the laptop budget would change the call toward file-level for the artifacts where it is too large, keeping records at generation and selection steps.

### Decision 17: The pipeline the first build targets
- Context: the first target is a pipeline shaped like soofi's; the checks need a pipeline whose capture points and intermediate files the tests can reach, and soofi's code cannot be copied (1.2).
- Options considered: (a) the project's own replica of soofi's published steps (5.2); (b) an existing pipeline framework (the Dolma toolkit, datatrove or NeMo Curator [CHECKED: Part 2, "Existing tools"]) as the target shape, wrapped by the tool; (c) soofi's published scripts run as they are.
- Trade-offs: (a) exposes every irreversible step's capture point (generation input, selection group, sanitizer log, the ids on the tokenizer's input), so each check asks the request's questions at each point and the plant list can reach them, but it only resembles soofi's pipeline; (b) shows fit to a real framework's data model, but that model decides which links exist, so the first build would answer a question about the framework, not about the soofi-shaped pipeline the request names; (c) is the exact target but unlicensed code (1.2, W4).
- Choice: (a).
- Why the others lost: (b) tests the wrong shape for this request's first target; (c) is barred by the request's constraint.
- Consequences: the adapters (3.3), an extension, read Dolma and datatrove outputs as evidence when switched on. An existing framework's pipeline shown to expose the same capture points (the generation parent list, the selection group, the tokenizer's input ids, the mixture snapshot) would change the call toward targeting it; a request to ship only a wrapper around such a framework would too.

### Decision 18: When a record counts as consumed
- Context: a step reads packed samples, a document can be split across two of them, and the request asks which checkpoints have evidence of exposure.
- Options considered: (a) consumed when any of its tokens is read; (b) consumed only when the whole document is read; (c) consumed when a share of its tokens above a set threshold is read.
- Trade-offs: (a) never gives "does not contain" for a checkpoint that read part of a withdrawn document, at the cost of counting a read of one token as exposure; (b) reports less exposure and lets a checkpoint that read most of a document answer "does not contain"; (c) needs a threshold the request does not give, and any threshold leaves some read text under a "does not contain".
- Choice: (a).
- Why the others lost: (b) and (c) let part of a withdrawn text be read under an answer of absence.
- Consequences: exposure counts count records read in this sense (2.4); Check 1 tests the split document's reported spans. A team that treats a read of a few tokens as no exposure would change the call toward (c), with its threshold recorded in each answer.

### Decision 19: When the step trace is written
- Context: checkpoint answers need what each step read, and the data-order cache files can be lost or replaced after a run.
- Options considered: (a) write each step's trace once, when the run is registered, from the cache files and the operator's step record, and answer from the store; (b) join from the cache files again at each query; (c) keep only the cache files and their digests, with no trace rows.
- Trade-offs: (a) lets answers survive a later loss of the caches and lets the trace be checked against the oracle once, at the cost of stored rows per step and a copy that could go stale if the files change (their digests are in the run segment, 3.1); (b) never stores a copy that can disagree with the files, but a lost or altered cache file silently changes old answers; (c) is the smallest, but the proof of 2.2(e) has no rows to walk.
- Choice: (a).
- Why the others lost: (b) lets an answer change because a file was lost; (c) leaves the proof nothing to check.
- Consequences: Check 2 registers each case in a fresh store; Check 5's trace faults change stored traces; trace bytes per step are measured (5.6). A team that cannot keep the store beside its run, or a measured trace size beyond the laptop budget, would change the call toward (b).

### Decision 20: A recorded "contains" against a failed proof condition
- Context: a checkpoint can show consumption of an affected record at one step and have an untraced step elsewhere; the answer must follow one rule.
- Options considered: (a) a recorded chain showing "contains" wins over a failed condition elsewhere; (b) any failed condition anywhere gives "may contain", even where consumption is shown; (c) a fifth answer, "contains, history partly untraced".
- Trade-offs: (a) keeps the shown exposure as the answer, since a missing record elsewhere cannot undo a recorded read, and the answer lists the untraced steps beside the chain (2.4); (b) is one uniform rule but discards exposure the tool has shown, so a team sees "may contain" where it knows "contains"; (c) keeps both facts but adds a state a team must learn.
- Choice: (a).
- Why the others lost: (b) throws away a positive finding; (c) adds a state for a case the chain already settles.
- Consequences: 2.2's closing paragraph and 2.4; Check 5's checkpoint 9 keeps "contains" under a segment-1 fault. A recorded chain shown to be wrong in practice, for instance a recovered link that fails verification later, would change the call toward (b).

### Decision 21: Where "not covered" ends and "may contain" begins
- Context: an artifact can lack its own record, or have its own record with a missing link, or sit downstream of an artifact that lacks one; a team needs to know which artifact to instrument.
- Options considered: (a) "not covered" only for an artifact whose own record is missing or unregistered, and "may contain" for anything downstream of it; (b) "not covered" for every artifact with anything missing in its ancestry; (c) no "not covered", only "may contain" (the three-answer vocabulary of Decision 8).
- Trade-offs: (a) points at the one artifact to instrument and still gives a downstream artifact with its own record an answer about its own links; (b) hides which artifact lacks the record, since a whole subtree reads alike; (c) is simpler but cannot tell an uninstalled pipeline from an incomplete one.
- Choice: (a).
- Why the others lost: (b) removes the pointer to the missing record; (c) is rejected in Decision 8.
- Consequences: Check 5 tests a deleted map and an unregistered checkpoint; the successor shard with a missing map answers "not covered" and its downstream "may contain" (4.4). Teams that want the whole subtree flagged at once would change the call toward (b) as a report view, not as an answer.

### Decision 22: When a step's last sample counts as fully read
- Context: the join resolves samples from the cache files, but a step's last sample could have been only partly read, and the tool must not let that turn into an unsupported "does not contain".
- Options considered: (a) a sample that resolves in full counts as whole, and an operator note can only lower it (F9, verified by Check 1 for a version); (b) a step is untraced unless the operator affirms whole-sample reads for it; (c) a per-token read log from the trainer is required.
- Trade-offs: (a) lets the tool answer for a run registered without any step notes, at the cost of over-reporting when a partial read goes unnoted (a "contains" or an exposure count above what was read, never a false "does not contain", L9); (b) guards only against that over-reporting and answers "may contain" for every checkpoint of a run whose operator affirmed nothing; (c) is exact where such a log exists, but the plan has no evidence that trainers write one.
- Choice: (a), with F9 and L9 marked.
- Why the others lost: (b) buys protection from a cost that is only over-reporting, with "may contain" for every un-affirmed run; (c) depends on a record the plan cannot show exists.
- Consequences: Check 1 verifies whole-sample resolution against the oracle's log for the version used; F6's "may contain" covers unverified versions, and the answer states the basis (2.4). A trainer shown to read tokens outside the samples the join resolves, not merely fewer of them, would change the call toward (b).

### Decision 23: The two restart points
- Context: the request asks where training restarts, and two answers differ: the last checkpoint with no exposure, and the first step at which the corrected data order diverges.
- Options considered: (a) report both, the exposure-free restart always and the exact-rerun restart for seeded runs; (b) report only the last exposure-free checkpoint; (c) report only the first step at which the corrected order differs.
- Trade-offs: (a) gives a restart that is safe for exposure and a restart that reproduces the corrected run, and says which holds, at the cost of two statements; (b) is the simpler and always available, but gives no step-level restart for a corrected rerun; (c) needs the corrected data order, which exists only for seeded runs.
- Choice: (a).
- Why the others lost: (b) cannot say where a corrected rerun diverges; (c) has no answer for an unseeded run or when the order change reaches the phase start.
- Consequences: 4.3, F7 and Check 9. A team that retrains from a checkpoint without caring about reproducing the corrected order would change the call toward (b).

### Decision 24: What a withdrawal selector names
- Context: a request says "a given source", and a source can have several revisions, as QA-base has before and after 16 Jul 2026 [CHECKED: Part 2, "The incident"].
- Options considered: (a) a source is a named set of members the team registered (revisions or parts of revisions, such as GPQA's folders inside a QA-base revision), expanded when the query runs, with the expansion listed in the answer, and a source with no registered member refused; (b) a single pinned revision per request, as the starting plan held; (c) a selector by content or metadata, such as a URL prefix.
- Trade-offs: (a) lets one request cover every revision of a source and shows which were included, but depends on the team's grouping; (b) is exact about one revision but needs one request per revision and misses revisions the team forgot to name; (c) reaches content with no registered source but needs metadata the first build does not read (L7).
- Choice: (a).
- Why the others lost: (b) leaves revisions out silently; (c) is refused in the first build rather than approximated.
- Consequences: 2.3 and the withdrawn-source answers list the members they expanded to. Under it a "does not contain" is scoped to the registered members (L12). A team that never groups revisions would change the call toward (b).

### Decision 25: Which handed inputs count as a generation output's parents
- Context: a job can be handed several records for one output and use only some of them; "contains" must not be reported for a source whose record the output did not use.
- Options considered: (a) a parent is a record the output used (the sole input, or stated by the output), and a handed record not stated as used is in scope only, is not a parent, and gives "may contain" for its source; (b) every handed record is a parent; (c) parents recovered by similarity.
- Trade-offs: (a) never reports "contains" for a source whose record the output does not state it used (the used list is process evidence, what the harness handed the job and what the output states it used, and not proof that the output depends on the source, and the answer says so), and keeps a job-level list usable for negatives, at the cost of "may contain" where a many-input job states nothing; (b) is the simplest but reports "contains" and retires records that do not depend on the source; (c) is excluded by the rule of L5.
- Choice: (a).
- Why the others lost: (b) over-reports exposure and over-retires; (c) can never be exact.
- Consequences: Check 5 asks the in-scope-only question and checks that a "contains" through a generation edge carries the note of 2.1; 4.1 lists such records as unresolved. A job that writes per-output usage would turn records in scope only into used records (parents) and change the call.

### Decision 26: What a listing states
- Context: the request asks which mixtures and checkpoints are affected, and an artifact nobody registered cannot appear in a list built from registered artifacts.
- Options considered: (a) a listing states what it covers and lists as "not covered" every artifact another record names but that has no record of its own; (b) a listing of the registered artifacts only, with no statement of coverage; (c) a listing refused unless the team supplies an inventory of expected artifacts first.
- Trade-offs: (a) makes the gap visible with no new input, but cannot show an artifact nobody named (L10); (b) lets a partial list read as complete; (c) closes that gap for the artifacts the inventory names, but makes every listing depend on a file the team may not keep.
- Choice: (a).
- Why the others lost: (b) hides absence behind a confident list; (c) blocks answers for teams without an inventory.
- Consequences: Check 5 asks that the deleted map's shard appear in the listing; L10 states the remainder. A team that keeps an inventory could add (c) as an optional input that lets the listing name expected-but-unregistered artifacts.

### Decision 27: How a mixture is recorded
- Context: a mixture is every binary shard in one directory, so what a run read depends on what the directory held when training started.
- Options considered: (a) a snapshot of the exact shard files and settings the trainer used, taken when training starts (3.1); (b) the training configuration alone (the directory path and settings); (c) a directory listing taken when the question is asked.
- Trade-offs: (a) lets a later query say which shards a run could have read, at the cost of one record per run segment; (b) records only where the shards were kept, so it cannot say which shards were there; (c) describes the directory as it is when asked, not as it was.
- Choice: (a).
- Why the others lost: (b) and (c) cannot say which shards the trainer saw, so a mixture answer would rest on a directory that may have changed (L6).
- Consequences: L6 states the answer when no snapshot exists; a run segment stores the snapshot (3.1). A trainer that selects shards by an explicit manifest, not by directory, would make (b) enough and change the call. ### Decision 28: Generating models and the records they generate
- Context: **[beyond the statement]** the rule of this decision goes past recorded derivation, so it is an extension (1.4); the question it lets the tool answer: can a record generated by an exposed model carry content from a source the model saw? A record generated by a model can carry content from a source the model was exposed to, through its weights and not through any record the job read; the request counts synthetic records among what is derived from a source, and their recorded derivation is covered by the edges (3.3); whether weight-borne exposure counts as derivation is the owner's call (Part 4: A10, B2, B3 6.2).
- Options considered: (a) record the generating model on every generation edge, read from the harness log, and carry its own exposure answer to its outputs; (b) record parents only and ignore the generating model; (c) treat every output of an exposed generating model as derived and retire it; (d) record the generating model on the edge as a logged attribute, answer from recorded derivation, and state in every negative that passes a generation edge that generating-model exposure was not assessed.
- Trade-offs: (a) lets the tool give "does not contain" for a record only when its generating model is "none" or a registered checkpoint that answers "does not contain", at the cost of no negative for any record whose generating model has no registered history, such as a hosted model, so the cost falls on every team that generates with a model it cannot register; (b) keeps a negative for every record but can say "does not contain" for a record that an exposed generating model produced, without saying so; (c) retires records that no derivation is shown for, so the successor differs from a from-scratch run without the source; (d) keeps the negative of (b), keeps the model on the edge so that (a) can be switched on later with no recapture, and says in the answer what was not assessed.
- Choice: (d) as the default of the proposed first build, with (a) as the extension the owner may switch on (3.3, Section 7); where (a) is on, the output of an exposed generating model answers "may contain" and not "contains" for a source its edge does not name, and keeps "contains" through a recorded chain to a confirmed affected parent (Decision 20) [BUILD COPY: A4].
- Why the others lost: (a) as the default withholds negatives from every shard and mixture that holds a record from a model with no registered history and from every checkpoint that read one (L11) before the owner has decided that weight-borne exposure is derivation; (b) reads absence from a record graph that omits a path to the source, with nothing in the answer to say so, which (d) adds; (c) breaks the equality that Decision 6 relies on.
- Consequences: F10 and L11; Check 5's model-entry row and Check 7's question about release R3 (extension rows, 5.5, run only when (a) is on); risk RK2 states the field cost when it is on. Evidence that a generating model's exposure rarely reaches its outputs would keep (d) and drop the extension; a team that registers its generating model's training run, or that must not give a negative past an exposed model, would switch (a) on and get the registered answer carried to the outputs.

### Decision 29: What identifies an occurrence
- Context: an occurrence is the unit every edge, map and answer hangs on, and the request needs lineage that keeps its history when the bytes do not change (a successor that re-sources a record, a release rebuilt with another dedup winner).
- Options considered: (a) the artifact's content digest plus a locator; (b) an id the store assigns at each registration, plus a locator; (c) an instance id derived from the content digest and the history that made the artifact (the producing step, the instance ids of its inputs and the artifact's own edge records, written as each child's locator, its parents' instance ids and locators and, for an "any" edge, the selected parent, 3.1) [BUILD COPY: A1], plus a locator.
- Trade-offs: (a) is simple and the same on every machine but gives two byte-identical artifacts with different histories one key, so their attributions could merge; (b) separates them but gives one artifact registered twice two ids, which splits its history and makes a re-registration look like a new artifact; (c) separates different histories, gives one id to one history registered again and can be recomputed on another machine from the same records, at the cost that a corrected history is a new instance, since recorded history is immutable.
- Choice: (c).
- Why the others lost: (a) cannot tell two histories apart; (b) cannot tell a re-registration from a different artifact.
- Consequences: 3.1; the digest conditions stay on the content digest (2.2(d), 3.4); Check 7's swapped-winner release is the test: the producing step and its inputs are the same, but the swap changes the edge records, so the two releases hold identical bytes and are two instances whose occurrences of X carry different keys. An import with no recorded producing step gets an instance from its content digest and member name, so the same bytes imported under two members are two instances, which is the scoping of L12. A need for ids that survive a corrected history would change the call toward (b).

### Decision 30: What the proposed first build covers

- Trade-offs: (a) builds the statement's three questions and keeps every rule and check already written, so the owner adds an item by switching it on, at the cost of a plan longer than the build it proposes; (b) builds five items the statement does not ask for and gives the builder their checks to write; (c) also takes the generating-model rule's cost by default, no negative for a record from a model with no registered history (L11), before the owner has decided it (Decision 28); (d) is the shortest plan and keeps the model field, but gives up design that the first debate settled (Part 4, 4.2), and an owner who later wants an item must have it designed and its checks written first.

- Why the others lost: (b) and (c) build beyond the statement by default, which makes the owner's scope choice for the owner (Part 4, 4.1); (d) throws away settled design and the written rules from which each item's result is stated to the owner (Section 7); it is the shortest and the most literal to the statement; (a) is proposed over it because Part 4, 4.2 says the plan must not get worse on what the first debate settled, and the owner may choose (d) (Section 7).
- Consequences: 1.4, 5.5 and Section 7 state the core, the extension rows and the owner's choices; Section 12 change 2 records the loosening this causes. An owner who wants the content ban or exposure counts in the first build would change the call toward (b) or (c) for that item; a plan too long for a builder to read would change it toward (d).

### Existing tools

Latest releases as of 14 Nov 2026, read from code and documentation.
- Dolma toolkit (Apache-2.0) [documented]: its tokenizer writes, beside each tokenized output, a .csv.gz row per document with id, src (source file), loc (line), start and end; its mixer stamps the input file and line on each document. It has no derived-from link, and its dedup marks a duplicate without recording which copy survived.
- datatrove (Apache-2.0) [documented]: an n-gram decontamination filter drops a document and marks the matched task; filters can write dropped documents with a reason; its tokenizer writes offsets without ids.
- OriginBlame (arXiv 2607.13037; MIT code; a research prototype with author-reported results in an unreviewed preprint) [documented]: a record can list several registered source sections; a token index links each document's token range to its sources; revoking an author, a section or a line hash produces a per-document forget bitmask. Its stated design limits: "single-hop provenance" (raw sources to final output, intermediate stages not traced) and "what is not recorded does not exist". The same text tracked from two sources gives two entries; the token index is rebuilt from scratch when the pipeline reruns with different data; it was evaluated with a GPT-2 tokenizer on Wikipedia, not with a Megatron writer. A paraphrase or translation pass is not documented; passing source references through one is a reading of its API [inferred].
- NeMo Curator, Data-Juicer, Hugging Face datasets, lakeFS, DVC and OLMo-core: no derived-from link found by a code search (weak evidence of absence). OpenLineage records lineage between datasets and down to columns; no row-level or document-id facet was found. Search indexes such as infini-gram return the positions of documents that contain a string, over their own index.
- Megatron-LM (core_v0.20.0): its licence is recorded inconsistently, a BSD-style LICENSE file with Apache parts against Apache-2.0 in its package metadata (unresolved); Megatron-Bridge is Apache-2.0 [documented].
- Practice [keyword reads; weak evidence]: decontamination before training is common; a documented retrain after contamination found post-release was not found; the post-release fixes found were data re-releases.

### Cost reference

- OriginBlame's authors report, on a Wikipedia workload [author-reported, unreviewed]: throughput drops of 1.3-4.0% in a Hugging Face pipeline and 2.1-19.0% in datatrove; a storage ratio of 1.33x at 1k pages, falling to 1.23x at 220k pages (712.4M tokens); and, in a 10k-record set, whole-dataset deletion over-deletes 1.3x or 101x depending on the revoked author's share (79.5% or 1.0%).
- No published cost of record-level lineage at trillion-token scale was found. Arithmetic only: two 16-byte references per edge take 32 GB per billion edges before indexes or compression.
